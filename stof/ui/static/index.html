Application & Login

config.json → target

That's all most targets need — STOF auto-detects the login form's fields on any application (no CSS selectors required). If a particular app's login page is unusual and auto-detect picks the wrong field, either set an exact override below, or use Workflows → Upload a workflow to capture the real login by recording it once with tools/record_workflow.py.

Advanced: manual selector overrides

Credentials

users.json + .env

Most targets only hand you one account -- that's the normal case, not a gap to work around. Add a second or third only if you actually have more than one (e.g. an admin and a read-only account) — every module and Verify Login already adapt to whatever's actually here, from one role up.

TOTP secret comes from the account's 2FA-enrollment QR code -- scan it with any generic QR reader (not an authenticator app) to read the raw otpauth://totp/...?secret=XXXX data, and paste just the secret= value above. Only app-based codes are supported -- SMS/push-approval MFA (Okta Verify, Duo push) can't be automated.

Neither fits (SSO/OAuth redirect to another domain, or a bot/CAPTCHA challenge)? Skip these fields and use Manual Session Cookies below instead.

Verify Login

runs a real login, shows you the result

Drives a real browser through the login form as the selected account and shows you a screenshot of what it actually reached — works the same whether this console is open on this machine or on another one over the network, since nothing pops up on the server's own screen.

Manual Session CookiesNot set

for targets STOF can't log into automatically

Log in as this account in your own real browser, then copy the cookie header from devtools (Network tab → any request → Cookie header, or Application → Cookies) and paste it below. The scan reuses this session directly and skips login entirely for this role. Note: a target that binds its cookie to the browser/network that earned it (e.g. Cloudflare's bot-challenge cookie) may still reject this if the scan runs from a different machine — this works reliably for ordinary session-cookie auth.

Crawl & discovery

automatic

STOF's authenticated Playwright crawler runs automatically at the start of every scan — there's nothing to configure here. It maps the target's real attack surface (pages, forms, API/XHR calls) as the logged-in role before any vulnerability module runs. If the target replays a recorded browser workflow (a multi-step login, a checkout flow), pick it below so the crawl and every module get to walk that path too.

Workflows

Record yourself performing a real multi-step flow once (login, checkout, a signup wizard) — pick it from the checklist when you start a scan and it's replayed early, extending what the crawler alone can reach.

How to record a workflow

runs on your own machine

Recording always happens on your own laptop with a small standalone script, fully offline from this server — no debug port needs to be reachable over the network, no matter where this console is deployed.

  1. Download the recorder script below.
  2. On your own machine: pip install playwright then playwright install chromium.
  3. Start a debuggable browser: google-chrome --remote-debugging-port=9222 --user-data-dir=/tmp/stof-chrome-debug &
  4. Run it: python3 record_workflow.py --output my-flow.json
  5. Walk through the real flow in that browser window — login, checkout, whatever the test case needs. Every click, fill, and page change is captured, across as many pages as the flow needs.
  6. Press Enter in the terminal to stop and save my-flow.json.
  7. Bring that file back here and click Upload a workflow above to import it.

Burp Suite Pro

Not set

Connects to a running Burp Suite Pro instance via its REST API (Settings → Suite → REST API in Burp). Evidence capture (proxying STOF's own traffic through Burp so it shows up in Proxy history) and Active Scan (Burp's own much slower vulnerability scanner) are separate toggles on purpose — turning one on never silently turns on the other.

Out-of-band collaborator

config.json → burp.collaborator_url

Point this at your own OOB collaborator (Burp Collaborator, interactsh, or any equivalent host you control) to enable ssrf_tests' TC-137.6 — it sends a unique callback URL per candidate parameter; STOF doesn't poll for the callback itself, so check your collaborator's own dashboard for a hit. One collaborator serves every application, so this stays here rather than on a per-target page.
